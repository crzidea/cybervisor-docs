# Runtime and Daemon (Developer Reference)

> **Audience: Developers** — Contributors extending the runtime, adapters, or hook system.

## Pipeline Lifecycle

For `gemini`, `claude`, `codex`, `opencode`, and `cursor` runs, `cybervisor` performs the following lifecycle:

1. Performs preflight checks.
2. Restores any skills left in `.cybervisor/backups/skills/` from a previous unclean shutdown (see [Skill Disable/Restore in User Guide](runtime-user.md#skill-disablerestore)).
3. Moves skills listed in `disabled_skills` from the project-local skills directory to `.cybervisor/backups/skills/<adapter>/`.
4. Writes shared hook runtime metadata into `.cybervisor/hooks/`.
5. Persists an exact settings snapshot in `.cybervisor/hooks/`.
6. Patches the active tool settings file so the selected agent invokes the packaged `cybervisor-agent-hook` entry point (verifier/stop hook only; the tool-use hook for write protection is managed per-stage, not at pipeline start).
7. For each stage, before the agent starts: if the stage defines `read_only_paths`, installs the `PreToolUse` (Claude Code) hook to block write-tool calls targeting those paths; Gemini, OpenCode, and Cursor enforce read-only paths via post-hoc filesystem snapshots (`ACPReadOnlySnapshot`) that detect and restore protected-file modifications after each turn; Codex app-server snapshots protected files before the turn and restores/fails on protected filesystem changes after the turn. If the stage has no `read_only_paths`, removes the tool-use hook (Claude) or skips adapter-level enforcement so the stage runs without it. This per-stage lifecycle means design stages get write protection while implementation stages run without the hook.
8. Starts the agent in a dedicated process group when supported. For Claude, the prompt is written to the agent subprocess's stdin. For Gemini, Codex, OpenCode, and Cursor, the prompt is delivered through ACP JSON-RPC (`prompt` method).
9. Uses the runtime hook to classify autonomy decisions as `approve` or `block`, then adapts those into the selected tool's native hook output so the agent continues autonomously.
10. If the active stage declares a contract, uses the same hook runtime to block completion until the required artifact exists and is structurally valid.
11. Streams agent output into stderr and the stage log file.
12. ACP adapter transports terminate the agent subprocess with bounded timeouts via `terminate_process()` (from `cybervisor.adapters._process`): close stdin, wait up to 5 seconds for a graceful exit, send SIGTERM and wait up to 2 seconds, send SIGKILL and wait up to 5 seconds. If the turn loop (`_run()`) raises an exception, `terminate_process()` is called in the error path before the exception propagates. The Claude adapter uses `BaseSubprocessAdapter`, which writes the prompt to stdin and closes it at start, then reads stdout until EOF and calls `process.wait()`; it does not use `terminate_process()`.
13. Re-validates contract artifacts after agent exit, then routes by contract status or explicit `next_stage` when configured.
14. Terminates the agent's descendant processes via `SignalHandler.terminate_descendants()`: sends SIGTERM to the process group (or individual PID on Windows), waits up to 2 seconds, sends SIGKILL to survivors, then falls back to individually tracked child PIDs. This runs in the `execute_stage()` finally block as a defense-in-depth safety net after adapter-level process termination.
15. Restores moved skills from `.cybervisor/backups/skills/` to their original project-local directories.
16. After the full pipeline loop, runs `SignalHandler.terminate_remaining_descendants()` as a safety net (CLI mode only; the daemon path relies on per-stage cleanup because it may host concurrent tasks): walks the process tree via `psutil.Process(os.getpid()).children(recursive=True)` to discover and terminate any orphans that escaped stage-level cleanup.
17. Restores settings and removes runtime files on success, failure, or interrupt.

## Live stderr and tool-call lines

ACP adapters emit canonical log events; adapter-local `tool_mapping.py` modules define how that agent's `session/update` tool kinds, titles, content types, and argument field names select shared formatters before events reach `stream_logging`. Rendered `tool call:` lines keep the original agent-visible tool name (for example `run_shell_command`) while using the mapped formatter name (for example `Bash`) only to summarize arguments. Adapters must not print final tool lines themselves or add agent-specific branches in the shared formatters; extend the owning adapter's mapping module when a new ACP tool payload shape appears.

## Adapter Compatibility

- **Gemini**: Uses Strategy B (runtime config only) — no native settings hooks are installed. Communicates with Gemini CLI over JSON-RPC via stdio (`gemini --acp --approval-mode default`), with a Gemini-specific `authenticate` step between `initialize` and `session/new`. The `methodId` sent to `authenticate` is extracted from current top-level `authMethods` responses or legacy `capabilities.authMethods` responses and normalized through a centralized legacy-to-valid mapping dict (`_LEGACY_TO_VALID_METHOD_ID` in `_acp_helpers.py`). Legacy values such as `google_login` are automatically mapped to the current valid enum value (`oauth-personal`). Update this dict when the Gemini CLI adds or renames auth method enum values. Read-only path enforcement uses `--approval-mode default` so Gemini emits `session/request_permission` before tool execution; `ACPReadOnlySnapshot` post-hoc restoration remains as belt-and-suspenders. The `--yolo`, `--sandbox`, and `--output-format stream-json` CLI flags are no longer used; the adapter communicates exclusively through ACP.
- **Codex**: The Codex app-server transport requires continuous stdin access for JSON-RPC messages. The Codex adapter does not use the stdin-prompt-write path and instead communicates through the app-server protocol. It starts Codex with config overrides `sandbox_mode="danger-full-access"` and `approval_policy="never"` plus matching thread/turn sandbox settings because Cybervisor supplies the outer sandbox/container boundary, and it answers app-server approval callbacks so non-interactive runs do not block. For `read_only_paths`, Codex uses two layers: (1) optimistic interception via `_server_request_result` — `item/fileChange/requestApproval` for protected paths receives a `deny` response, and `item/permissions/requestApproval` excludes protected patterns from filesystem entries; (2) reliable post-hoc enforcement via `CodexReadOnlySnapshot` — matching files are snapshotted before the first turn, modified/deleted/created protected files are restored after each turn, and the attempt fails with a read-only-paths error if any protected path changed. The snapshot is the primary enforcement layer; the interception layer is optimistic.
- **OpenCode**: Uses Strategy B (runtime config only) — no native settings hooks are installed. Communicates with OpenCode over JSON-RPC via stdio (`opencode acp`), with a verify-and-continue loop that sends continuation prompts when the verifier blocks (same pattern as Codex). After `session/new`, the adapter calls `try_set_default_approval_mode` with `exclude_mode_ids=frozenset({"build", "plan"})` — OpenCode's "build" and "plan" modes are agent execution modes that lack permission semantics, so they are excluded from consideration. When no genuine permission-asking mode remains after exclusion, no `set_mode` call is made and `enforcement_mode` is `"post_hoc_only"` at construction time. If a non-excluded mode is found and `set_mode` succeeds, a first-turn health check detects when zero `session/request_permission` events arrived — a one-time WARNING is logged identifying the mode as an agent execution mode (not a permission-asking mode) and a corrective `"post_hoc_only"` marker is appended to `hook-events.jsonl`. For model selection, the adapter reads the user's OpenCode model configuration from global and project config files and injects the effective model via `OPENCODE_CONFIG_CONTENT`, which takes highest precedence in OpenCode's config resolution. Cybervisor `stage_models` overrides take precedence over the user default. Cybervisor does **not** create or modify `opencode.json` in the workspace — all runtime overrides (model, permissions) are injected via `OPENCODE_CONFIG_CONTENT`. After session creation, `session/set_model` is attempted as a secondary best-effort call. The adapter verifies the model was applied by inspecting the `session/new` response and logs a WARNING if the active model differs. The adapter generates native OpenCode permission configuration from Cybervisor's `disallowed_tools` and `read_only_paths` and injects it via `OPENCODE_CONFIG_CONTENT`. File-context ingestion is disabled through three mechanisms: (1) the generated runtime config sets `instructions` to an empty array; (2) `OPENCODE_DISABLE_PROJECT_CONFIG=true` and `OPENCODE_DISABLE_CLAUDE_CODE=true` are set in the subprocess environment to suppress project-level config discovery and Claude-specific context ingestion; (3) legacy `fileContext` and `contextPaths` keys are stripped from the merged config to prevent runtime errors on current OpenCode releases. Subprocess crashes during initialization (before ACP session establishment) are detected and reported immediately rather than waiting for the full timeout; dead processes in the continuation loop fail fast instead of sending prompts to an exited subprocess. Read-only path enforcement uses `ACPReadOnlySnapshot` post-hoc snapshots as a belt-and-suspenders backstop regardless of proactive mode status. The `--dangerously-skip-permissions` and `--format json` CLI flags are no longer used. `OPENCODE_ENABLE_EXA=1` is injected into the subprocess environment via `ACPAdapterBase.extra_env` to enable Exa search integration.
- **Cursor**: Uses Strategy B (runtime config only) — no native settings hooks are installed. Communicates with Cursor over JSON-RPC via stdio (`cursor-agent acp`), with a Cursor-specific `authenticate` step (method `cursor_login`) between `initialize` and `session/new`. Auth credentials reach the subprocess via inherited environment variables (`CURSOR_API_KEY` or `CURSOR_AUTH_TOKEN`) or a prior `cursor login`. The adapter generates native Cursor CLI permission configuration from Cybervisor's `read_only_paths` settings and writes it to the project-level `.cursor/cli.json` before launching the agent. The existing config (if any) is backed up and restored after the session ends. Deny rules use Cursor's `Write(pathOrGlob)` permission type to proactively prevent writes on protected paths. After `session/new`, the adapter calls `try_set_default_approval_mode` to switch from yolo to a non-yolo approval mode if the agent advertises one. A first-turn health check detects when `set_mode` reported success but zero `session/request_permission` events arrived — a one-time WARNING is logged. An `enforcement_mode` marker (`"proactive"` or `"post_hoc_only"`) is written to `hook-events.jsonl` at session start. Read-only path enforcement uses `ACPReadOnlySnapshot` post-hoc snapshots as a belt-and-suspenders backstop regardless of proactive permission status. The adapter does not use CLI flags like `--dangerously-skip-permissions`.

## Run-Daemon Coordination

When `cybervisor run` is invoked (both bare-prompt and explicit `run` subcommand), it checks whether the daemon is reachable before acquiring the local `.cybervisor/instance.lock`. If the daemon is reachable and has any active task (status: `"running"`), `run` exits `1` with a message showing the running task ID and stage, directing the user to `attach` or `cancel`. This prevents `run` instances from executing concurrently with daemon-submitted tasks in the same directory. When the daemon is unreachable, `run` falls back to the standard `.cybervisor/instance.lock` mechanism.

**CWD normalization:** Task matching resolves symlinks and normalizes paths (including trailing slashes). This means `/workspace`, `/workspace/`, and symlinked paths to the same directory all resolve to the same canonical path, ensuring nested task detection is not bypassed by symlinks or trailing slashes.

## Generated Artifacts

- `.cybervisor/logs/cybervisor.log.jsonl`: structured run log
- `.cybervisor/logs/stages/<stage_name>.jsonl`: captured transcript per stage
- `.cybervisor/backups/<stage_name>/<timestamp>/`: versioned backups of stage artifacts after successful completion; each timestamped directory preserves one run's artifacts; never wiped by the artifact reset step
- `.cybervisor/contracts/artifacts/*.yaml`: optional stage-result artifacts for contract-enabled stages; before each stage execution, all top-level files in this directory (except the current stage's own artifact) are removed so agents are not confused by stale artifacts from prior stages — nested subdirectories are preserved
- `.cybervisor/hooks/hook-events.jsonl`: runtime event log for hook decisions, contract validation failures, ACP permission decisions (allow/deny for disallowed tools), ACP snapshot-based read-only enforcement events (`enforcement` for Gemini/OpenCode/Cursor), Codex snapshot-based read-only enforcement events, and an `enforcement_mode` marker written at ACP session start (`"proactive"` when `session/set_mode` succeeded and the agent emits permission requests, `"post_hoc_only"` when proactive enforcement is unavailable or no genuine permission-asking mode was found). A corrective `"post_hoc_only"` marker with `"correction": true` is appended when the first-turn health check detects that `set_mode` succeeded but zero `session/request_permission` events arrived. Each line is a JSON object with timestamp and event type. Check this file when debugging unexpected blocks or permission decisions.
- generated contract guidance is derived from each stage's `contract.routes` and contract field definitions in `cybervisor.yaml`

## Client Subcommand Reference (Daemon Mode)

- **`cybervisor status`** — sends a `ping` message; exits `0` if the daemon is reachable, `1` otherwise. When the daemon is reachable, it reads the extended `pong` response containing active task snapshots (protocol v2) and prints running task IDs and stages. Tasks with status `"completed"` or `"cancelled"` are excluded from the display. For tasks registered but not yet started (active_stage is `null`), the output renders `"initializing"`.
- **`cybervisor submit`** — sends a `run` message; streams all pipeline events and returns the pipeline exit code on `run_complete`. Accepts a positional prompt argument or reads the task description from stdin when no argument is given (e.g., `printf "task" | cybervisor submit`). If both a positional argument and piped stdin are present, the positional argument takes precedence. When no prompt is provided and every stage in the effective slice has a self-contained `prompt_template`, the task runs without an objective prompt (config-driven promptless execution). When no prompt is provided and any stage still requires `{objective}`, the command exits with an error listing the stages that need a prompt.
- **`cybervisor attach`** — sends a `resume` message; when `task_id` is omitted, pings the daemon to find running tasks in the current directory and auto-resolves to the sole one (errors with "No active task to attach to." if zero tasks; errors with "Multiple tasks are running in this directory." if more than one); replays buffered events (handling chunked payloads automatically), then subscribes to live events until the task reaches a terminal state.
- **`cybervisor cancel`** — sends a `cancel` message; when `task_id` is omitted, the daemon uses the client-provided `cwd` to find and cancel the running task in the current directory (same disambiguation rules as `attach`); the daemon responds with `pipeline_abort` followed by `run_complete` on the canceler's own connection. The client exits `0` on `pipeline_abort`, `1` on error.
- **`cybervisor logs`** — sends a `resume` message; drains all buffered events and outputs each as a JSON line to stdout.
- **`cybervisor end`** — sends a `set_stop_stage` message; accepts `--after <stage>` (stop after this stage executes, same as the old `--stage` flag) or `--before <stage>` (stop before this stage starts, skipping it); `--after` and `--before` are mutually exclusive. An optional positional `task_id` explicitly targets a specific task; when omitted, the daemon uses the client-provided `cwd` to find the running task in the current directory. Both `--after` and `--before` are updatable mid-run via the daemon's `set_stop_stage` message — the runner checks the `EndStageRef` dynamically at each stage transition, so a subsequent `end` command can change the stop point while the pipeline is running. This mid-run update capability is daemon-mode only; direct `run` mode has no `EndStageRef` wiring and the `--end-after`/`--end-before` flags are fixed at invocation.

All client commands accept `--host` and `--port` to override the daemon address. Defaults come from `~/.cybervisor/config.yaml` (`server.host`, `server.port`). The connection timeout is 5 seconds; commands exit `1` with a "daemon not reachable" message on timeout or connection failure.
